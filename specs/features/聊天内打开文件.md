# 聊天内打开文件 · 需求澄清

> 依据：用户澄清（2026-08-31，第二次：明确「替换系统打开行为」）｜ 文档版本：v2.0 ｜ 状态：✅ 方案已定稿，进入实施

## 背景与问题

聊天消息流中涉及项目文件的元素（agent 产出文件的行 chip、助手消息中可点击的 inline-code mention），点击后当前行为是调用**系统默认应用打开**——Windows 上文件未关联应用时弹出「选择应用」对话框，体验割裂。用户期望：**在 DSH 窗口内直接打开**该文件（复用文件树面板编辑器）。

## 现状核对（已定位链路）

| 环节 | 位置 | 说明 |
|------|------|------|
| 打开入口 | `workspaces.openPath(path)`（runtime 服务） | 系统打开：`api.host.openPath`；**全 DSH 唯一调用者是聊天 openFile 回调**（`dsh-client-ui-conversation` chat 条目 inject，L9772） |
| 消费方 1 | ProducedFiles 组件（`dsh-client-ui-deliverables` turnTail 槽） | 文件行 chip 点击 → `owner.openFile(path)` |
| 消费方 2 | `chatFileMentions` 服务（ui-deliverables） | 助手消息 inline-code mention resolver → `owner.openFile(path)` |
| 路径语义 | 两处均先 `resolveWorkspacePath(cwd, path)` | 传给 openPath 的是**绝对路径** |
| 可复用能力 | `filetree/fileStore.openFile` + `store.setPanelOpen` + `store.setReveal` | DSH 窗口打开已有完整实现 |
| host 能力 | `fs-service.stat`（已实现，缺路由） | 区分文件/目录 |

## 方案（v2.0）

**拦截 `ctx.workspaces.openPath`**（实例方法 shadow 包装，唯一调用者即聊天文件打开，影响面单一）：

```
openPath(path) 被调用
  → fetch host stat(path)
    → stat 成功 且 type === 'file' 且 路径在当前会话工作区内
        → DSH 打开：setPanelOpen(true) + filetree openFile(path) + setReveal(path)
    → 否则（目录 / 工作区外 / stat 失败 / 无 cwd）→ 回落原系统打开
```

- 目录（含「打开所在文件夹」的 `.` 场景）保持系统打开；工作区外文件保持系统打开
- host 新增 `GET /api/dsh-develop-ui/fs/stat?path=` 路由（复用 `fs-service.stat`）
- 生命周期：apply 内 `ctx.effect` 包装，dispose 恢复原方法；模块级防重复包装标志

## 功能范围

| 项 | 范围 |
|----|------|
| 拦截对象 | `workspaces.openPath`（聊天文件打开链路；sidebar 等不调用，无影响） |
| DSH 打开条件 | stat=文件 + 工作区内 |
| 回落 | 目录 / 工作区外 / 判定失败 → 原系统打开（`.catch` 语义不变） |
| 工作区判定 | 路径规范化后以当前会话 cwd 为前缀（cwd 取 `sessions.list.byId[current]?.cwd`） |

## 验收标准

- [ ] 聊天中 agent 产出文件（行 chip）点击 → DSH 窗口打开，不再弹系统「选择应用」
- [ ] 助手消息 inline-code mention 点击 → DSH 窗口打开
- [ ] 聊天中「打开所在文件夹」（目录）→ 仍走系统打开
- [ ] 工作区外文件（如桌面文件）→ 仍走系统打开
- [ ] 文件树面板关闭时点击 → 自动打开面板并聚焦编辑器标签
- [ ] 图片文件 → 跟随文件树图片预览逻辑
- [ ] 插件卸载/重载 → openPath 恢复原行为（无残留包装）
